# Comparative build benchmark

Runs the same synthetic project through pledgepack, esbuild, rolldown, rspack and
vite, and reports **speed**, **output size** and **output quality**. It exists so
that any "faster than X" or "smaller than X" claim about pledgepack has a
reproducible number behind it (see `docs/BENCHMARK.md` for why that matters).

## Run

```bash
cd bench
npm install                      # installs the competitors (not pledgepack)
node run.mjs                     # 300 and 2000 modules, 5 runs each
node run.mjs --modules 300 --runs 3 --tools pledgepack,esbuild
node run.mjs --pledge-bin /path/to/pledge
```

The pledgepack binary is looked up in this order: `--pledge-bin`, `$PLEDGE_BIN`,
`../target-bench/release/pledge`, `../target/release/pledge`. **Use a release
build.** The harness labels debug builds and prints a warning, but their numbers
are meaningless. On Windows without MSVC:

```powershell
$env:CARGO_TARGET_DIR = "target-bench"; $env:RUSTUP_TOOLCHAIN = "stable-x86_64-pc-windows-gnu"
cargo build --release -p pledgepack-cli
```

Results are written to `results/latest.md` and a timestamped `.json` + `.md`.

## Remote cache scenario

`--tools pledgepack-remote` runs pledgepack against a throwaway local HTTP
server (`remote-server.mjs`) that implements pledgepack's `PUT /cache/<key>` /
`GET /cache/<key>` remote-cache protocol. It is excluded from the default
`--tools` list (it needs the server and measures a different thing — a cold
build with a *shared team* cache already warm, not a solo warm/cold pair) so
opt in explicitly:

```bash
node run.mjs --modules 300,2000 --runs 5 --tools pledgepack,pledgepack-remote
```

None of esbuild/rolldown/rspack/vite have an equivalent built in, so there is
no comparison row for them — this column exists to show what pledgepack's own
remote cache is worth, not to race it against something else.

## Plugin-cache scenario

`--tools pledgepack-plugin` runs pledgepack with a JS plugin (`tools.mjs`'s
`SLOW_PLUGIN_SRC`) whose `transform` hook does deliberately expensive,
deterministic work and opts into pledgepack's plugin-output cache via
`cacheable: true`. Also excluded from the default `--tools` list — same
reason as `pledgepack-remote`, no equivalent column exists for the other
tools:

```bash
node run.mjs --modules 100 --runs 5 --tools pledgepack-plugin
```

What this demonstrates: on a warm rebuild with unchanged sources, pledgepack
skips the plugin's `transform` call entirely (content-hash + plugin
fingerprint keyed — `crates/js-plugin-host`), where esbuild has no
persistent cache at all and would re-run it on every invocation. It is
**not** a separate caching mechanism from the one `pledgepack`'s own
cold/warm columns already show (Tier 3's cache work covers this too) — it
exists to make the plugin-specific share of that saving visible on its own,
since a fixture with only cheap built-in transforms wouldn't show much
difference either way. `runs in Node and correct` on this row reflects the
same known linker bug as the plain `pledgepack` row, not anything
plugin-specific.

The fixture's `pledge.plugin.json` sets `pluginSecurity.requireSigned:
false` so it can load an unsigned plugin — a benchmark-only simplification;
real projects should sign plugins (`pledgepack plugin sign`) or opt out of
signing deliberately themselves, not inherit it from here.

## Gate mode

`--gate` (optionally with `--max-cold-ratio <n>`) exits non-zero if
pledgepack's output regresses: fails to run, dead code survives, the dynamic
import isn't split, or (with `--max-cold-ratio`) its cold build is more than
`n`x the fastest competitor. Wire this into CI once the linker/tree-shaking
work lands, so a regression fails the build instead of quietly slipping in:

```bash
node run.mjs --modules 300,2000 --runs 5 --gate --max-cold-ratio 3
```

## What is measured

Every tool is configured for the same job: production mode, minify, tree-shake,
ESM output, source maps, `process.env.NODE_ENV` defined as `"production"`,
dynamic imports split into their own chunk. Configs are generated by `tools.mjs`
so they can be reviewed in one place.

| metric | how |
|---|---|
| **cold build** | wall time of the whole process (runtime startup included), output and caches wiped before each run, one discarded run first. Median of `--runs`. |
| **warm build** | same, but persistent caches are kept (only the output dir is removed). Tools with no persistent build cache should show warm ~ cold. |
| **JS output / gzip / brotli** | sum over all emitted `.js` files (gzip level 9, brotli 11). |
| **runs in Node and correct** | the entry is executed with Node and its stdout must equal what `node --experimental-strip-types src/main.ts` prints for the source. Catches output that builds but does not work. |
| **dead barrel / lib exports left** | 30 unused exports behind a barrel file and 40 unused exports of a `sideEffects:false` package; each carries a unique marker string that is grepped for in the output. Ideal: 0. |
| **unreachable file emitted** | a file nothing imports. Ideal: no. |
| **dev-only branch kept** | code under `process.env.NODE_ENV !== 'production'`. Ideal: no. |
| **dynamic import split** | the lazily imported module lands in a different file from the entry. |

The fixture (`generate-fixture.mjs`) is deterministic: N modules in a binary
tree (all reachable, each called once) that all import one shared util, plus the
probes above. Modules are tiny, so this measures per-module overhead and graph
handling rather than minifier throughput on large real-world code.

## Known limits (read before quoting numbers)

- Synthetic project, TypeScript only: no CSS, images, JSX or framework code.
  Add a real project under `fixtures/` before drawing conclusions about those.
- Wall time includes each tool's own startup (Node for vite/rolldown/rspack, a
  native binary for esbuild/pledgepack). That is what a user experiences, but
  at small sizes it dominates.
- No memory measurement, no dev-server cold start, no HMR latency, no
  incremental (watch) rebuild timing. Those need a browser or a long-lived
  process and are not implemented yet.
- Tools have different defaults for what "minify" means and which syntax level
  they emit; sizes are comparable within a few percent, not exactly.
- Single machine, other processes running: treat differences under ~20% as noise.
